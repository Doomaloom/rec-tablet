Start here

Rec Tablet is a native Linux app for a five-inch landscape touchscreen. A swim instructor imports classes before a lesson, then records attendance, assesses skills, and reviews feedback. Lesson work stays on the device; the normal app has no server or lesson-time network dependency.

make run                         # launch through go run
make test                        # software-rendered tests
make build                       # creates dist/native/rec-tablet
./dist/native/rec-tablet --fullscreen
Good first tour: run the app, hold My Classes for three seconds, import examples/classes.json, then follow Attendance and Skills. Launch with go run ./cmd/rec-tablet --database /tmp/tour.sqlite3 for disposable data.

Architecture at a glance

The code is organized by workflow and feature, similar to Angular feature folders. Each swimming feature keeps its repository interface in model.go, actions and screen state in controller.go, native presentation in view.go, and tests beside them.

The application constructs these objects explicitly. The shared shell hosts feature content and handles common navigation controls; it never checks for swimming screen names. Features depend on small repository interfaces, so controller tests can run with simple fakes. Domain functions do not depend on SQL or Fyne.

Think in features: changing attendance normally means opening the attendance folder. A new equipment workflow gets its own folder alongside swimming, with its own models and rules.

Common presentation lives in named shell components, named layout slots, and UI primitives. SQLite configuration lives in platform/database; swimming owns its schema and curriculum initialization.

Screens and state

Swimming's navigation coordinator uses typed routes and a Frame with swimming-specific parameters. Each registered feature builds screen state and handles its own actions. The coordinator uses the shell's generic history stack; features navigate through the coordinator without importing one another.

shell.State describes common chrome and provides a ComposeBody callback. The feature view draws content through ui.Surface. The shell's ComposeScreen function assembles named components from component factories; the shell renders headers, paging controls, and the footer. Optional OnLeave callbacks release feature resources on route changes or close.

Successful actions refresh state. Failed actions restore navigation and the selected date while displaying the error. A 120 ms guard prevents one physical tap from activating the next screen; detached controls are disabled and their hold timers stopped. Draft persistence remains in SQLite.

SQLite data model

The schema lives in internal/workflows/swimming/repository/schema.sql and uses PRAGMA user_version = 1. Foreign keys, WAL journaling, full synchronous writes, and a busy timeout protect local work.

Core workflows and rules

Attendance

A tap upserts the status for one lesson and enrollment and commits immediately.

Skill completion

An observation succeeds only when every subskill is checked. Three successful observations complete a skill. The student list for the selected skill shows up to three green progress segments, and holding a student for two seconds removes that student's newest check.

Drafts

Every mark persists immediately. A partial draft survives navigation and restart but does not affect progress. Selecting the same lesson, swimmer, and skill resumes it.

Corrections

Editing a submitted attempt creates a draft. Submission records old answers in revisions, replaces results, and recalculates success transactionally.

Feedback

Feedback shows assessed, incomplete skills and uses the latest completed observation to identify unsuccessful criteria or successes still needed.

Version isolation

Courses and attempts keep their curriculum version, so catalog updates cannot reinterpret historical work.

Add a swimming feature

  1. Create a feature folder with model.go, controller.go, view.go, and tests. Declare only the repository operations it needs.
  2. Add typed routes and parameters to swimming navigation. Implement the navigation.Feature contract and give each route a named body composer.
  3. Construct and register the feature in module.go. Add a navigation action in the relevant existing feature.
  4. Add typed repository operations and domain rules only where needed. Keep SQL out of the controller and preserve transaction boundaries.

Add an unrelated workflow

Create a sibling of swimming, implement shell.Presenter, and supply its own screen state and content. Use shell.History with that workflow's route type. Wire it into application startup when its entry flow is designed. The test-only equipment workflow demonstrates this without any swimming imports.

Design the new workflow's persistence and data coexistence when its requirements are known. Do not rename swimmers into a universal entity or require equipment checks to have lessons. Shared packages contain infrastructure and reusable presentation.

Tests and builds

make test       # all packages with Fyne's software driver
make race       # race detector
make vet        # static checks
make smoke      # headless render and screenshot
make package    # Linux archive with binary, icon, and docs
REC_TABLET_SCREENSHOTS=/tmp/rec-tablet-screens go test -tags ci ./internal/workflows/swimming -count=1

Read attendance controller tests for fake repositories, domain tests for pure rules, and repository tests for atomic writes and recovery.

Swimming interaction tests and file-dialog tests cover the assembled app. Sister export tests preserve the contract. An architecture test prevents shared infrastructure from importing workflows and features from importing SQL or sibling features.

The ci build tag uses Fyne's software driver. It verifies behavior and layout without claiming physical hardware, GPU, waterproofing, or wet-touch validation.

Current boundaries

  • The POC covers aquatics attendance, skill assessment, corrections, and feedback.
  • Automatic sync, result import upstream, accounts, free-text parent notes, lesson plans, and timers are future work.
  • Session and device management across datasets is still manual.
  • Waterproofing, submerged touch, and battery endurance require the device trial.
Design rule: keep swimming rules and schema inside swimming. New workflows own their concepts and use the common shell and platform. The current app still launches directly into My Classes, with unchanged v1 data and file formats.
