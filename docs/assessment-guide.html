01 · Start here

An assessment records a swimmer’s work on one curriculum skill. Each skill contains criteria, called subskills in the code.

The feature can assess one swimmer, a class queue, a group, or a timed heat. All modes use enrollment records.

Three successful attempts complete a skill.

A submitted attempt succeeds only when all its criteria succeed. An unsuccessful submitted attempt increases the assessed count, but not the success count.

ConceptMeaningCode
DraftAn answer map that the app can change. A draft does not add to submitted progress.drafts.answers
Submitted resultA saved observation with criterion results and a submission time.attempts + results
CorrectionA draft for an existing attempt. Submission replaces results and stores their previous values.revisions
CompletionAt least three submitted successful attempts for an enrollment, skill, and version.RequiredSuccesses = 3

This guide covers every Go file in assessment/, including tests. It also covers eight files that define its main external connections.

The function guide includes every declared function and method in those files. Callback behavior appears in the file explanations and flow descriptions.

02 · Code structure

The parent component selects a mode. Each mode builds screen state and provides actions. Views draw controls from that state.

The repository owns SQL writes. Domain values carry data between packages. Shared helpers define mode availability, benchmarks, and common actions.

How the connections work

module.go creates the assessment parent and registers its routes. bindings.go creates the five child components.

Each child receives a Storage value. Its fields are functions from the repository. A child does not need the complete Store API.

common.Navigation supplies route operations. shared.Actions supplies view actions. This design permits component tests with small fake callbacks.

Build starts with InitialState. It reads the course and roster through LessonContext. It then creates common.Input.

The selected mode returns a screen state. Its ComposeBody callback draws the body. The shell provides the header, rails, and footer.

Sources: module.go · assessment/component.go · assessment/bindings.go

04 · Single assessment and correction

Trace a normal attempt

  1. Select an eligible swimmer.
  2. Mark the criteria that succeed.
  3. Select Save to submit the observation.

NewAttempt validates the enrollment, lesson, and skill. It reuses a pending attempt for the same enrollment, lesson, skill, and curriculum version.

Each normal checklist tap writes to drafts.answers. A second tap removes that answer. It does not store a final failure yet.

Save submits the observation.

The comment above SaveAttempt refers to an incomplete attempt. The function calls Submit.

The repository fills missing criteria with not_yet. It stores an unsuccessful submitted attempt when any criterion lacks success.

Example

A skill has three criteria. You mark two as successful. Save writes two successful results and one not_yet result.

The assessed count increases by one. The success count stays the same. The draft is removed after submission.

Switch swimmers on the large display

SwitchPerson opens or reuses the selected swimmer’s draft. It replaces the active frame. It does not submit the previous swimmer’s draft.

Each swimmer retains a separate draft. The Save and Discard rails affect only the active attempt.

Correct an existing attempt

Selecting an attempt calls EditAttempt. The repository copies its saved results into a draft if no draft exists.

The new assessment frame sets Review = true. Compact review shows one criterion per page. Large review shows all criteria.

When the correction submits, the repository stores the previous answer map in revisions. It replaces the results on the same attempt.

A correction can change the progress count. It does not create another attempt. Leaving review without submission leaves its database draft available.

05 · Class assessment

Class mode opens one pending attempt for every active swimmer at the selected level. It does not use attendance.

The route page selects a swimmer in the pending queue. Criteria appear together. Taps write directly to that swimmer’s database draft.

ControlStorage callEffect after success
Save current studentSubmitAttempts([current ID])Label the swimmer Saved. Remove the swimmer from the pending queue.
Discard current attemptDiscardAttempts([current ID])Label the swimmer Discarded. Remove the swimmer from the pending queue.
Save all pending attemptsSubmitAttempts(all pending IDs)Submit the whole queue in one transaction. Leave class mode.
Discard all pending attemptsDiscardAttempts(all pending IDs)Delete the whole pending queue in one transaction. Leave class mode.

After a successful single-swimmer action, the component clamps the route page to the shortened queue. It returns when the queue becomes empty.

The original roster remains available for status labels. Large mode disables entries marked Saved or Discarded.

Class discard deletes reused drafts.

Class entry can reuse an existing unfinished draft. Class discard calls DiscardAttempts, which deletes that draft and its attempt.

Group mode uses a different discard operation. It can restore the draft that existed before the group session.

06 · Group assessment

Prepare the groups

Multi entry reads the roster and attendance for the selected lesson. It keeps active swimmers at the skill level whose attendance is present.

Group setup stays in memory. It creates no attempts until every assignment passes Ready.

BalancedSizes distributes the remainder to the first groups. Ten swimmers in three groups produce capacities of four, three, and three.

A swimmer can belong to only one group. Each group must reach its capacity. All eligible swimmers must have an assignment.

Changing the group count rebuilds groups and clears assignments. Returning with the same count preserves the assignments.

Mark the results

ConfirmSelection calls OpenMultiAttempts for all assigned swimmers. The repository creates new drafts or reuses existing pending drafts.

Each returned MultiAttempt records whether it was created. It also contains the original answers of a reused draft.

Pass sets every criterion to successful in one draft write. The incomplete control opens a temporary checklist.

Temporary checklist taps change only StudentEdit.Answers. Student Save writes successful criteria and fills all others with not_yet.

Student Discard or another screen exit clears the temporary edit. The database draft retains its earlier answers.

Finish the groups

Save group submits every member of the current group in one transaction. Save all submits every pending group in one transaction.

Discard group uses DiscardMultiAttempts. It deletes new attempts and restores original answers for reused drafts.

The component removes a group only after storage succeeds. When no groups remain, it clears session state and returns to the previous route.

A table page is not a group.

Large mode shows six members per local table page. Save group still affects the complete group, including members on other table pages.

07 · Timed heats

Timed mode measures several swimmers against one benchmark. The participants share a clock and lap target. Each participant has a separate attempt.

Skill IDDistance labelDuration used by SaveAdditional label only
Splash7:10100 m3 minutes100 yd · 2:40
Splash8:9200 m6 minutes200 yd · 5:20
Splash9:11300 m9 minutes300 yd · 8:00

The labels show yard times, but the save calculation uses the metric duration in Benchmark.Limit. No yard-limit choice exists in this path.

Set up and run a heat

  1. Select the swimmers.
  2. Enter a lap target from 1 to 999.
  3. Continue to the heat screen.
  4. Select Start.
  5. Tap a swimmer after each completed lap.
  6. Select Save to submit all participants.

Compact setup uses a separate lap screen. Large setup places the swimmer grid beside the keypad. Both create a paused heat.

NewTimedHeat rejects a swimmer with an unfinished attempt for the same lesson, skill, and version. Creation uses one transaction.

A lap tap works only while the clock runs. The repository increments the lap count up to its target.

The final required lap records CompletedAt. Later taps do not change that swimmer. Other swimmers can continue.

Calculate the result

success = participant.Completed
          && participantElapsed <= benchmark.Limit

Completed swimmers use their fixed finish time. Incomplete swimmers use the heat’s elapsed time at Save. Incomplete swimmers receive an unsuccessful result.

The component stops its refresh ticker before Save. If storage fails while the heat was running, it restores the clock and refresh activity.

The repository writes the supplied Success flag to every criterion. It does not calculate the benchmark limit itself.

What survives a restart

Stored timed rows retain lap targets and lap counts. The active clock, completion flags, and finish times live in component memory.

The current feature does not reconstruct an active heat from those rows after restart. Persistent lap data alone cannot restore the original clock.

08 · Stored data

The database separates pending work from submitted observations. The attempt ID connects the answer map, results, revisions, and timed measurements.

Submission rules

submitAttempt validates supplied answer IDs and values. It adds not_yet for missing criteria. All successful criteria produce a successful attempt.

SubmitAttempts rejects empty batches and duplicate IDs. It requires every selected attempt to be pending and to have a draft.

A batch error reverses that transaction’s writes. A successful batch commits every selected attempt together.

Progress counts only attempts with a submission time. It filters by enrollment, skill ID, and curriculum version.

There is no lesson filter in the progress query. Successes can accumulate across lessons for the same enrollment and curriculum version.

Latest-success removal

A two-second hold can remove the latest successful attempt. The repository orders by submission time, creation time, and row ID.

Removal deletes the attempt’s results, revisions, draft, and timed data in one transaction. This action removes history as well as progress.

Two kinds of page state

The route frame owns Page. For class mode, that value selects a pending swimmer. For group results, it selects a group.

The components also own local panel pages. large.Pages points to those values. They select visible roster rows or result rows.

Large layouts use all data rows in their component state. Their own grids select visible subsets. Save scope comes from the mode session.

Text fitting

Large checklists use two columns above six criteria. A shared font starts at 20 and can decrease to 14.

Compact class checklists divide the body into equal rows. Their shared font starts at 22 and decreases until the labels fit.

The header helpers use compact titles when full titles exceed available height. They keep the complete title in primary information.

Tests measure every bundled curriculum skill. These checks cover the current catalog and chosen dimensions. They do not guarantee every possible future label will fit.

10 · Errors and code findings

What Run restores

navigation.Run copies the route history and date before an action. It calls Refresh when the action returns no error.

If the action or refresh fails, Run restores history and date. It sets an error notice. It does not undo committed database writes.

Run also does not restore every field in child component state. Class and group actions therefore wait for storage success before removing pending entries.

Quiet storage failures

Several single and timed actions return nil after a storage failure. They usually keep the current screen and its existing work.

Those failures do not reach Run as errors. They can leave the user without a notice. Class and group batch actions usually return errors.

Writing method

This guide applies ASD-STE100 Issue 9 writing principles. Descriptions use short sentences, active verbs, and consistent technical terms.

Instructions use command verbs and one action per sentence. Code identifiers retain their exact spelling. The table above defines the main technical terms.

A complete dictionary and part-of-speech audit has not been performed. This guide does not claim certified conformity.
